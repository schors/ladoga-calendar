# Ладожский календарь

## Назначение проекта

«Ладожский календарь» — современный авторский календарь для Ладожского озера, Невы и восточной части Финского залива. Он записывает обычные гражданские даты через ближайший праздник и собственный счёт лет: «В третий день Тёмной воды, в лето 1274-е.» Цель — машиночитаемые данные, по которым простой скрипт получает готовую русскую дату без собственного расчёта праздников и склонения числительных.

Подробное устройство календаря и формат данных описаны в `docs/ladoga-calendar.md`. Проект времени суток — в `docs/ladoga-time.md`. Отложенные замечания по стилю и образам — в `docs/style-notes.md`.

## Характер календаря и работа с источниками

- Весь календарь имеет статус `authorial` (поле `status` в `ladoga-definitions.json`). Его применение к прошлым годам — условная датировка по правилам проекта.
- У каждого праздника поле `origin` показывает, на что опирается образ (например, `authorial_local` или `documented_folk_motif`), а `date_status` у всех праздников равен `project_convention`: сама дата назначена проектом.
- Различай происхождение образа, историческое свидетельство об обычае и назначение конкретной даты. Источник о корюшковой путине не подтверждает существование исторического Корюшкиного дня 26 апреля.
- Новые праздники могут быть авторскими. Для них прямо указывай авторство названия, даты и обычая. Исторические утверждения снабжай проверяемыми источниками через `sources` и `source_ids`.
- Сохраняй местный характер: вода, дороги, ремесло, природа, дом, память, песни и совместная трапеза. Названия должны быть выразительными и понятными.
- Географическая опора — Ладожское озеро, Нева и восточная часть Финского залива. Волхов и Старая Ладога остаются историческим истоком: от них идёт счёт лет, к ним относится источник о купальских гуляньях. Новые образы бери прежде всего с Ладоги, Невы и залива.
- Город на Неве в текстах календаря по названию не называй. В библиографических сведениях источников (`title`, `publisher`) название остаётся таким, как у источника.
- Пользовательские тексты и описания пиши по-русски. Технические ключи и идентификаторы сохраняй на английском. Все комментарии в программном коде и примерах кода пиши только на английском.
- Названия пор времени суток не должны повторять образные слова из названий праздников (вода, огонь, вечер, день, ночь, ветер, тёмный) и начинаться отдельными словами «после», «до», «за»: так начинаются фразы о дне. Названия мест — Нева, Ладога, залив — допустимы. Подробнее — `docs/ladoga-time.md`, раздел 2.
- В основном названии праздника сохраняй выбранное написание «Вяйнемяйнен». Другие написания и `Väinämöinen` могут находиться в `aliases`.

## Устройство репозитория

| Путь | Что это |
| --- | --- |
| `ladoga-definitions.json` | Единственный источник правил: эра, праздники, шаблоны фраз, слова для чисел, события по наблюдению, источники, диапазон сборки. Правится вручную |
| `scripts/build_calendar.py` | Генератор: собирает `data/` из `ladoga-definitions.json`, кроме `data/sun/` |
| `scripts/build_sun.py` | Считает восход, полдень и закат для `data/sun/`; единственный скрипт, которому нужна библиотека из `vendor/` |
| `scripts/ladoga_time.py` | Показ времени суток для момента по файлам `data/` |
| `vendor/astronomy-engine/` | Astronomy Engine 2.1.19, один файл и его лицензия MIT. Не правь: замена — только новой версией с новым SHA-256 в определениях |
| `tz/Europe/Moscow` | Закреплённый файл часового пояса (tzdb 2026e). Замена — только вместе с SHA-256 и `sun_data_revision` |
| `data/index.json` | Оглавление: диапазон, языки, пути к файлам, подсказки потребителю |
| `data/ru/holidays.json` | Названия и описания праздников для показа |
| `data/ru/YYYY.json` | Готовые русские данные одного гражданского года |
| `data/ru/time.json` | Названия пор и шаблоны подписей времени |
| `data/time/YYYY.json`, `data/sun/YYYY.json` | Время суток по дням и солнечные события |
| `scripts/check_calendar.py` | Независимая проверка правил и готовых данных |
| `scripts/build_images.py`, `docs/img/` | Картинки для README (SVG), рисуются по `data/`; после изменения данных перерисовать, `--check` сверяет |
| `fonts/kurale/` | Шрифт Kurale (SIL OFL 1.1) для картинок, встраивается в каждую SVG. Замена — только вместе с SHA-256 в `build_images.py` |
| `README.md`, `LICENSE` | Описание для людей; лицензия CC0 1.0 (общественное достояние) — на всё, кроме `vendor/` (MIT), `fonts/` и встроенного в `docs/img/` шрифта (SIL OFL 1.1) и `tz/` (tzdb, общественное достояние) |
| `docs/ladoga-calendar.md` | Устройство календаря: правила, праздники, формат данных, проверки и контрольные случаи |
| `docs/ladoga-time.md` | Время суток («Ладожское время»): сезонные часы, восемь пор, данные и проверки |

Файлы в `data/` создаются только генераторами. Вручную их не правят.

Текущие версии, диапазон и числа записей перечислены в `docs/ladoga-calendar.md`, раздел «Текущая версия». При согласованном изменении диапазона или набора праздников обновляй данные и этот документ вместе.

Утверждены календарь и формат данных. Язык реализации, интерфейс приложения и способ развёртывания выбираются по задаче и фактическому состоянию репозитория. Сначала изучай существующие файлы и команды; не считай инструменты, которыми данные были получены раньше, установленной архитектурой проекта.

## Документация

- `docs/ladoga-calendar.md` описывает сделанный календарь. Если меняются правила, формат данных, праздники или контрольные случаи, обновляй его вместе с определениями, скриптами и `README.md`.
- `docs/ladoga-time.md` описывает время суток. Если меняются поры, опорная точка, правила расчёта или формат файлов времени, обновляй его вместе с определениями и скриптами.

## Изменение и воспроизводимость данных

- Любые изменения праздников, правил, шаблонов, слов для чисел и диапазона вноси только в `ladoga-definitions.json`, затем пересобери данные: `python3 scripts/build_calendar.py`.
- Не исправляй файлы в `data/` вручную.
- Генератор сначала собирает все файлы в памяти, потом записывает каждый через временный файл и только после этого удаляет устаревшие файлы: `build_calendar.py` — в папках языков и в `data/time/`, `build_sun.py` — в `data/sun/`.
- Правки описаний и библиографических сведений не требуют изменения датировок, если вычисления и отображаемые формы остаются прежними.
- Изменение готовых подписей или датировок отражай в `calendar_version`. Изменение структуры файлов — в `schema_version`, с описанием способа перехода.
- Сохраняй стабильные `id` и совместимость существующих путей доступа.
- При изменении календарного содержания явно перечисляй, какие даты, названия или правила изменились. Изменение набора опор может поменять датировки окружающих дней.
- Не вводи случайный выбор праздника или варианта фразы. Одинаковые определения должны давать побайтно одинаковые файлы.
- Команды генерации и проверки документируй после их появления и проверки в репозитории; не выдумывай отсутствующие команды, каталоги или CI.

## Проверка изменений

Нужен только Python 3.11 или новее, сторонние библиотеки не требуются (библиотека для `build_sun.py` лежит в `vendor/`).

```bash
python3 scripts/build_sun.py --check        # data/sun/ matches the definitions byte for byte
python3 scripts/build_calendar.py --check   # the rest of data/ matches ladoga-definitions.json byte for byte
python3 scripts/check_calendar.py           # independent check of definitions and data
```

Запускай все три после любого изменения. Если менялся раздел `time` (точка, солнечные события, закреплённые файлы), сначала пересобери `python3 scripts/build_sun.py`, потом `python3 scripts/build_calendar.py`. При успехе `build_sun.py --check` печатает `OK: 14 sun files match`, генератор — `OK: 31 files match`, а проверка — сводку (число лет, дат, високосных лет, праздников, наибольшее смещение, число солнечных дней, наибольшее расхождение с эталонной формулой Солнца, число контрольных случаев времени) и строку `OK`; все завершаются с кодом 0. При ошибках они печатают `FAILED` и список проблем и завершаются с кодом 1.

`build_calendar.py --check` ничего не записывает: он собирает данные в памяти и сравнивает с файлами в `data/`, включая лишние и недостающие файлы в папках языков и в `data/time/`. `build_sun.py --check` так же сверяет `data/sun/`. Без `data/sun/` генератор не работает: эти файлы — его вход.

`check_calendar.py` не использует генератор и не доверяет определениям: у него свои эталоны праздников, слов для чисел и правил построения фраз. Что именно он проверяет, описано в `docs/ladoga-calendar.md`, раздел 10.

Поэтому **любое намеренное изменение праздника** (даты, названия или формы) нужно внести в двух местах: в `ladoga-definitions.json` и в таблицу `REFERENCE_HOLIDAYS` в `scripts/check_calendar.py`. То же для поры — таблица `REFERENCE_PORAS`, для опорной точки — `REFERENCE_LOCATION`. Так же при изменении модели обновляются контрольные случаи — в таблице раздела 10 `docs/ladoga-calendar.md` и в скрипте.

Для правок только документации или описательных полей достаточно проверки затронутых утверждений и структуры; полный пересчёт нужен при изменении результатов календаря.
