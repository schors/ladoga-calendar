# Ладожский календарь

## Назначение проекта

«Ладожский календарь» — современный авторский календарь для Старой Ладоги, Нижнего Поволховья и южного Приладожья. Он позволяет записывать обычные гражданские даты через ближайший праздник и собственный счёт лет:

> На второй день после Тёмной воды, в лето 1274-е от ладожского начала.

Проект соединяет славянские народные мотивы, карело-финскую эпическую традицию и местную жизнь: Волхов, Ладогу, лодки, ветер, белые ночи, лес, корюшку и долгие зимние вечера. Придуманные праздники — сознательная часть замысла. Корюшкин день и Вечер Вяйнемяйнена добавлены по прямому пожеланию пользователя.

Практическая цель — машиночитаемые данные, по которым простой скрипт может получить красивую, однозначную русскую дату без собственного расчёта праздников и склонения числительных.

## Характер календаря и работа с источниками

- Весь календарь имеет статус `authorial` (поле `status` в корне JSON). Его применение к прошлым годам — условная датировка по правилам проекта.
- У каждого праздника поле `origin` показывает, на что опирается образ (например, `authorial_local` или `documented_folk_motif`), а `date_status` у всех праздников равен `project_convention`: сама дата назначена проектом.
- Различай происхождение образа, историческое свидетельство об обычае и назначение конкретной даты. Источник о корюшковой путине не подтверждает существование исторического Корюшкиного дня 26 апреля.
- Новые праздники могут быть авторскими. Для них прямо указывай авторство названия, даты и обычая. Исторические утверждения снабжай проверяемыми источниками через `sources` и `source_ids`.
- Сохраняй местный характер: вода, дороги, ремесло, природа, дом, память, песни и совместная трапеза. Названия должны быть выразительными и понятными.
- Пользовательские тексты и описания пиши по-русски. Технические ключи и идентификаторы сохраняй на английском. Все комментарии в программном коде и примерах кода пиши только на английском.
- В основном названии праздника сохраняй выбранное написание «Вяйнемяйнен». Другие написания и `Väinämöinen` могут находиться в `aliases`.

## Эра и гражданские даты

Базовый календарь — григорианский. Все праздники сохраняют свой месяц и число во всём диапазоне и при любом его расширении. Юлианское преобразование не применяется. Даты Солнцеворота, Весеннего поворота, Осенин и Коляды являются фиксированными символическими опорами; астрономические моменты отдельно не вычисляются.

Собственная эра называется «Лета Ладоги»:

```text
ladoga_year = gregorian_year - 752
```

753 год принят за первое ладожское лето по археологической дендродате. Выбор этой эпохи условен; он не устанавливает точный год основания поселения. Историческая основа описана в источнике `ia_ladoga` основного JSON.

Номер лета меняется **1 января**. Коляда не меняет номер года.

| Гражданский год | Ладожское лето |
| --- | ---: |
| 2025 | 1273 |
| 2026 | 1274 |
| 2027 | 1275 |
| 2038 | 1286 |

Календарный часовой пояс — `Europe/Moscow`. Если на входе уже гражданская дата, не сдвигай её через UTC. Если на входе timestamp, сначала получи местную дату в указанном часовом поясе. Граница суток — местная полночь.

## Правило выбора опорного праздника

1. Для датируемого гражданского года построй наступления праздников предыдущего, текущего и следующего годов.
2. Выбери наступление с минимальным абсолютным расстоянием в календарных днях.
3. При равном расстоянии предпочитай прошедшее наступление. Если остаётся совпадение нескольких праздников, используй порядок массива `holidays`.
4. Рассчитай `offset_days = target_date - anchor_date` как разность календарных дат.
5. Ладожский год вычисли по самой датируемой дате. `anchor_year` относится к конкретному наступлению опорного праздника и может отличаться.

Смещение `0` означает сам праздник, `+1` — следующий день, `-1` — канун. Отрицательное смещение показывает, сколько дней осталось до опоры, положительное — сколько прошло после неё. Не используй деление разности Unix timestamp на 86 400 для подсчёта календарных дней.

Опорное наступление может находиться за пределами диапазона файла. Например, для `2025-01-01` используется Коляда `2024-12-21` со смещением `+11`. Поэтому кандидатов нельзя ограничивать только годами из диапазона файла.

Готовая подпись формируется по правилам текущего JSON:

- В сам праздник — индивидуальная `on_day_phrase`.
- В канун — «В канун {name_genitive}».
- На следующий день — «На следующий день после {name_genitive}».
- Для других будущих опор — «За {количественное числительное словами} {день/дня/дней} до {name_genitive}», например «За пять дней до Коляды».
- Для других прошедших опор — «На {порядковое числительное словами} день после {name_genitive}», например «На третий день после Купалы».
- Полная строка: «{day_text}, в лето {ladoga_year}-е от ладожского начала.»
- Краткая запись: «{ladoga_year} · {short_name}» и через пробел смещение со знаком, например «1274 · Купала -1». В сам праздник смещение не пишется: «1274 · Корюшка».

Формы названий бери из данных. Не выводи русские падежи из `id` или `short_name`.

## Контракт JSON

| Раздел | Назначение |
| --- | --- |
| `schema_version`, `calendar_id`, `name`, `status`, `locale`, `region`, `timezone`, `range` и другие поля верхнего уровня | Общие сведения о календаре и файле |
| `era` | Эпоха, формула года и начало нового лета |
| `date_policy` | Постоянные гражданские даты и правила их интерпретации |
| `formatting` | Выбор опоры, смещения и шаблоны |
| `holidays` | Определения праздников, формы названий и источники |
| `years["YYYY"]` | Ладожский год, фраза года, високосность, число дней и `holiday_dates` |
| `dates["YYYY-MM-DD"]` | Полностью подготовленная запись дня |
| `observed_events` | Определения событий по наблюдению и зарегистрированные наблюдения |
| `sources` | Проверяемые источники с идентификаторами |
| `usage` | Краткая подсказка потребителю: по какому пути брать готовые значения |
| `examples` | Примеры, согласованные с основным индексом |

Ежедневная запись содержит:

```json
{
  "ladoga_year": 1274,
  "anchor_id": "vainamoinen",
  "anchor_date": "2026-12-07",
  "anchor_year": 2026,
  "offset_days": 3,
  "day_text": "На третий день после Вечера Вяйнемяйнена",
  "text": "На третий день после Вечера Вяйнемяйнена, в лето 1274-е от ладожского начала.",
  "short": "1274 · Вяйнемяйнен +3"
}
```

Это запись для `2026-12-10`. Обычный потребитель читает `dates[date].text`; для другого оформления доступны `day_text`, `short` и `years[year].year_phrase`. Потребителю не требуется собственный календарный или морфологический движок.

Сохраняй типы: годы и смещения — целые числа, даты — строки, признаки високосности — boolean. Ключи объектов `years` являются строками. Для даты вне диапазона сообщай об отсутствии записи; не подставляй ближайшую дату или другой год.

## События по наблюдению

Отдельно предусмотрены `ice_breakup` — Вскрытие Волхова, `first_smelt` — Первая корюшка, `first_hoarfrost` — Первый иней и `freeze_up` — Ледостав.

У них нет назначенных ежегодных дат. Наблюдение содержит `event_id`, `date`, `location` и `observer_note`. В текущей версии список наблюдений пуст и `included_in_date_index` равен `false`.

Не заполняй прошлые и будущие годы вымышленными наблюдениями. Фиксированный Корюшкин день и реально замеченная Первая корюшка — разные записи. Добавление наблюдения само по себе не меняет готовые датировки; для включения таких событий потребуется явно определённый режим и пересчёт.

## Изменение и воспроизводимость данных

- Начинай с фактических определений и правил в JSON и существующего генератора, если он есть в репозитории.
- Разделяй исходные определения праздников и производные ежегодные/ежедневные записи. Для изменений, требующих пересчёта, используй воспроизводимую генерацию.
- После изменения опорных дат, порядка выбора, названий или их грамматических форм согласованно обновляй `years.holiday_dates`, `dates`, `examples` и связанные метаданные. Не исправляй отдельные строки готового индекса вручную.
- Правки описаний и библиографических сведений не требуют изменения датировок, если вычисления и отображаемые формы остаются прежними.
- Сохраняй стабильные `id` и совместимость существующих путей доступа. Несовместимое изменение структуры отражай в `schema_version` и описывай способ перехода.
- При изменении календарного содержания явно перечисляй, какие даты, названия или правила изменились. Изменение набора опор может поменять датировки окружающих дней.
- Не вводи случайный выбор праздника или варианта фразы в основной индекс. Одинаковые входные определения должны давать одинаковый результат.
- Команды генерации и проверки документируй после их появления и проверки в репозитории; не выдумывай отсутствующие команды, каталоги или CI.

## Проверка изменений

Команда проверки (нужен только Python 3, сторонние библиотеки не требуются):

```bash
python3 scripts/check_calendar.py                 # checks ladoga-calendar-2025-2038.json
python3 scripts/check_calendar.py path/to/other.json
```

Скрипт заново вычисляет каждую ежедневную запись из определений праздников и сравнивает с данными. Готовые записи из `dates` для расчёта он не использует. При успехе печатает сводку и `OK` и завершается с кодом 0, при ошибках печатает список проблем и завершается с кодом 1. Контрольные случаи из таблицы ниже записаны в скрипте; при намеренном изменении модели обновляй их в обоих местах. Числительные в скрипте заданы до 12; если наибольшее смещение станет больше, дополни их.

После изменений вычислений или генерации проверяй корректность JSON без повторяющихся ключей, непрерывность диапазона, состав годов и високосных дней, уникальность идентификаторов и разрешение `source_ids`.

Для каждой ежедневной записи должны выполняться:

```text
ladoga_year = target_date.year - 752
anchor_year = anchor_date.year
target_date = anchor_date + offset_days
```

Опора должна соответствовать правилу ближайшего праздника. Годовые даты праздников, примеры и полные/краткие подписи должны согласовываться с определениями. Смысловую проверку выбора опор выполняй независимо от проверяемой реализации.
